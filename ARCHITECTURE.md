# App Architecture Documentation

This document outlines the architectural standards and patterns used in the NetManager Mobile application.

## 1. Offline-First Strategy

The application employs a robust offline-first strategy to ensure field technicians can work in areas with poor or no connectivity.

### Core Components:
- **`DatabaseService`**: Manages a persistent sync queue using `AsyncStorage`. It stores `SyncQueueItem` objects which include the URL, method, payload, and metadata.
- **`useApiMutation`**: A custom TanStack Query hook that acts as the primary interface for data-modifying operations (POST, PUT, PATCH, DELETE).
    - If the device is online, it performs the request immediately.
    - If a network error occurs or the device is explicitly offline, it automatically pushes the operation to the `DatabaseService` queue.
    - It handles optimistic-like behavior by notifying the user that data is saved locally.
- **`SyncService`**: A background service that monitors network connectivity using `NetInfo`.
    - When connectivity is restored, it automatically triggers `processQueue()`.
    - It processes items in batches with concurrency control (using `p-limit`).
    - It handles complex multi-step syncs, such as uploading local images before sending the final API request.
    - Permanent failures (4xx errors) are removed from the queue and reported to the user via local notifications.

## 2. Data Fetching Pattern

We use **TanStack Query (React Query)** for all data fetching to provide a smooth "stale-while-revalidate" experience.

- **`useApiQuery`**: The standard hook for GET requests.
    - **Caching**: Data is cached in memory and persisted (where configured) to provide instant loading on subsequent visits.
    - **Offline Support**: If the network is unavailable, the hook returns the last cached data, allowing the UI to remain functional.
    - **Automatic Refetching**: Data is automatically refreshed when the app regains focus or the network reconnects.

## 3. UI Standards

### Atomic Design
The `src/components` directory follows the Atomic Design methodology:
- **Atoms**: Basic building blocks (Buttons, Inputs, Badges, Skeletons).
- **Molecules**: Groups of atoms working together (NotificationBell, SelectionModal).
- **Organisms**: Complex UI sections (DashboardHeader, PerformanceStats, Feature-specific modules).
- **Templates**: Page-level layouts (ParallaxScrollView).

### Loading States
- **Skeletons**: We avoid full-screen loading spinners. Instead, we use specific `Skeleton` components (e.g., `WorkOrderSkeleton`, `DashboardSkeleton`) to provide a "perceived performance" boost.
- **`SelectionModal`**: A standardized, searchable modal component used for selecting items (Customers, Employees, Products) throughout the app.

## 4. Security

### Authentication
- **Tokens**: JWT session tokens are stored securely using `expo-secure-store`.
- **Interceptors**: The centralized `api.ts` Axios instance uses request interceptors to automatically attach the `Authorization` header to every request.
- **Unauthorized Handling**: A response interceptor detects 401 Unauthorized errors and automatically triggers the logout flow via `DeviceEventEmitter`.

### Data Integrity
- **Signing**: Sensitive offline operations use `generateSignature` from `utils/crypto.ts`.
- **Signing Key**: The `OFFLINE_SIGNING_KEY` is managed via Expo constants (`expoConfig.extra`) to keep it out of the source code while remaining accessible for offline signing.

```text
  /services         # Business logic & API clients (Database, Sync, etc.)
  /utils            # Helper functions (crypto, logger, formatting)
  /constants        # App-wide constants and theme
  /native           # Native module bridges
```
